# 从 rea-video 借鉴环境美术管线：项目对照与落地建议

> 2026-11-18 补充：已再次核对 rea-video 的实际代码和本项目新交接文件。阶段 A 的入口与问题队列已部分落地；本次增量结论见第 8 节。此前调查记录保留，不把待实施建议改写为已实现能力。
> 同日后续：用户要求整体管线改造，并补充 Agent 找参考图的质量要求。已据此更新 [完整管线说明](envart-pipeline-skill.html)、skill 及案例接续记录；第 8 节仍作为改造前的调查快照，不能代替现行执行协议。

## 结论

**值得借鉴，但最有价值的不是视频模型、分类算法或更长的 skill，而是把“观察 → 判断 → 制作 → 复核”变成可追溯、可局部重做的工作流程。**

本项目已经有真实素材、可编辑 Godot 场景、固定机位、素材来源、冻结截图与失败记录。当前主要瓶颈不是“能不能生成场景”，而是：能否准确读懂参考，提前淘汰不合适的主体素材，并把用户的美术反馈持续用于下一轮。建议先补这些环节，不重写现有项目，不扩大到全场、多引擎或通用 Agent 平台。

优先顺序：

1. **参考拆解与主体素材小样前置**：先确认空间、形体、表面和光影关系，再铺场景。
2. **轻量环境交付包与结构化复核**：给人看图片，给 Agent 看紧凑索引；结论绑定实际证据。
3. **有范围的修订与经验复用**：知道改什么、影响哪些机位、哪些证据需要重新生成。

### 对当前项目的具体判断

不是从零开始。已有几项基础很值得保留：

- `skills/godot-envart/SKILL.md` 已明确素材优先、空间意图、整墙重复、活动道具组、真实截图和适度验证。[E2]
- 四游戏试验记录诚实区分了自由布局与白盒约束、首次独立产出与反馈后修订，也明确记录失败。[E3]
- 最新局部已经把内容、灯光和相机分开组织，保存了前后场景、截图与部分文件哈希。[E4]
- 本次查看 `interior-glazed/room.png` 与 `detail-01/room.png`，可见货架、交接车和纸品让档案交接活动更可读，墙面信息也增加；这说明局部反馈有用，但不能由此推出整体达到 Control 水平。[E5]

缺口主要在“把这些经验组织成下一次能直接使用的输入”。例如安装器清楚记录了选中的文件与哈希，但并不是通用选材系统；构建脚本包含具体模型、尺度和坐标，设计选择与实现紧密混在一起。现有说明也明确警告重建会覆盖手工改动。[E1][E6]

## 3. 最值得迁移的八个思路

### 3.1 先逆向拆解参考，而不是直接从风格名生成场景

rea-video 把画面来源、包装、声音、人物和制作路线拆开，不用一个总标签解释整条视频。[R1][R2]

对应到环境任务，先回答：

- **空间**：室内/室外/半开放？哪些围护被省略，哪些确实不存在？
- **形体**：建筑高宽比、开口节奏、大中小体块之间是什么关系？
- **表面**：连续还是分格？细节主要来自几何、材质还是贴花？在哪个距离能看清？
- **活动**：这里发生什么事情？哪些物体必须成组、有支撑和朝向关系？
- **光影**：稳定主光和局部光来自哪里？焦点、阴影与远近层次如何建立？
- **非环境因素**：角色、UI、粒子、战斗闪光、景深和后期分别贡献了什么？

**本项目一个很具体的例子**：`control-3.jpg` 和 `control-4.jpg` 都含强烈战斗特效、悬浮碎屑及人物遮挡。不能把爆炸造成的亮区或红色效果全当作场景常驻照明，也不能从单张图推断完整空间和准确灯光参数。[E5]

拆解应同时保存两条线：

1. **参考里看见什么**：事实、图像位置、来源和不确定点。
2. **这次准备如何实现**：可用素材、允许适配、白盒约束、成本与替代方案。

能复现画面关系，不代表知道原作真正使用了什么资产或渲染技术。需要高风险决定而证据不足时，先问用户或补参考，不把猜测固化进场景。

### 3.2 把“看见的、测得的、推断的、用户决定的”分开

rea-video 的逐镜数据区分确定性结果、VLM 回答、Agent 复核和用户纠正；`aspects` 更明确地并列来源，不把所有值平均成一个答案。[R3][R4][R6]

环境任务中也应区分：

| 类型 | 示例 | 用途 |
| --- | --- | --- |
| 可测事实 | Godot 内门洞净宽；模型包围盒；贴图缺失；相机 FOV | 工具验证，不靠看图猜 |
| 图像观察 | 整墙上重复污渍明显；柜侧比桌子简化很多 | 关联具体图片、区域与观看距离 |
| 推断 | 可能是顶部采光；可能需要局部重做 UV | 保留依据和待确认项 |
| 用户决定 | 保持这条路线；本次要室内；不接受这种墙面 | 作为本任务约束，不由自动评分抵消 |

不能用“有法线贴图”证明材质好，不能用“放了很多道具”证明细节丰富，也不能用“碰撞没变”证明视觉没有堵路。[E2][E3]

不建议照搬 rea-video 的分类融合权重。美术质量没有对应的分类真值；初期用“已核实 / 待确认 / 有分歧”比随意填写 87% 置信度更可靠。

### 3.3 借鉴 VIDEO.md 的分层交付，而不是增加更多散落文档

rea-video 从同一份数据生成两种读法：人看报告，Agent 按卡片、地图、时间线和单镜文件逐层读取。[R2]

建议试验一个仓库内约定的 `ENVIRONMENT.md`：**不是现成标准，不需要马上制定通用 schema。**它只是任务入口，告诉下一位 Agent：目标、范围、当前版本、主要差距、哪些地方不能改、接下来该读哪个文件。

最小包可以是：

```text
一个现有局部试验/
├── ENVIRONMENT.md          # 简短目标、区域/机位索引、状态、下一步
├── brief.md                # 参考观察、目标要求、白盒保护；人工维护
├── asset_manifest.json     # 沿用现有来源记录，补候选取舍和小样证据
├── review.json             # 每个问题的证据、影响、修订目标与处理状态
├── captures/<pass>/        # 不覆盖旧轮次；附场景/相机/依赖版本信息
└── *.tscn                  # 实际可编辑场景，不把全部节点复制成另一份 JSON
```

可链接既有文件，不必第一天拆出很多主题文档。只有一个文件大到影响阅读时再拆分。

**归属必须明确**：人工维护的 brief 和用户反馈不由报告生成器覆盖；场景负责真实对象和变换；截图负责画面证据；HTML 和索引是可再生的视图。否则“结构化”反而多出一套容易过期的数据。

### 3.4 让视觉复核变成可执行任务，并真正反馈到计划

rea-video 的 `build_tasks()` 会提出必须看的图、优先级和问题；`apply_answers()` 校验并保存答案，之后 `finalize()` 更新结论和制作计划。它还故意不在任务里展示另一个 VLM 的答案，以减少照抄。[R3][R4]

当前项目已有详细复核记录，但可以让每条反馈更容易执行和追踪：

```text
问题：主体墙面出现明显重复污渍
证据：第 02 轮 room 机位、右侧整墙、对应参考裁切
影响区域：records-wall
影响机位：room、props、door
优先级：进入细节装饰前必须解决
修订：先比较两个候选整墙小样，不用新增杂物遮挡
复核条件：新场景重新加载后出图；目标距离看不到显著重复母题
状态：待处理 / 已修改待看图 / 已复核 / 用户接受
```

复核优先级不能只看不确定性，还要看**视觉影响和返工代价**：确定很差的主建筑也必须先处理。主体、空间、主要表面不成立时，暂停加小道具。

分别记录技术检查、参考贴合、内部一致性、用户接受。不能把前三项的自评自动转成最后一项。

### 3.5 区分观察单位与制作单位：机位不是区域

rea-video 将剪辑镜头重新组织成生成单元或拍摄场次，并考虑同场景、输入限制和复用，而不是机械地每镜从零做一次。[R5]

在环境管线里，可对应为：

- **机位**：观察和验收的单位，例如整体、门洞、道具近景。
- **区域**：实际修改的单位，例如入口、档案交接区、坡道过渡。
- **素材/材质**：跨区域共享的资源。
- **关系**：纸品由货架支撑、灯具照明工作区、通路需要避让等。

三个机位可能都看到同一个货架；一堵墙也可能影响两个区域。不能按截图分别布置出互相矛盾的场景。

先用稳定的区域名、节点路径和资源引用表达这些联系即可，不需要完整知识图谱。活动道具组适合逐渐沉淀成可编辑子场景，但只提取真实重复使用的组合，不先建一整套 prefab 工厂。

### 3.6 能力地图应变成“素材与制作方式的适用性记录”

rea-video 的能力地图记录原语、具体模型的限制、来源、验证日期和不确定性；代码会读取部分能力来选择输入模式与生成分段。[R5][R7]

环境任务可借鉴它的决策形式，而不是搬来模型排行榜：

| 需求 | 优先制作路线 | 必须先确认 |
| --- | --- | --- |
| 主体建筑、近景道具 | 已有授权资产或实际下载素材 | 轮廓/比例/尺度/材质是否适合参考 |
| 模块缺一个尺寸或开口 | 针对性 Blender 适配 | 不破坏保护尺寸，适配是否比换资产合算 |
| 连续墙面与表面变化 | 适合的材质 + 必要着色/贴花 | 整墙重复、细节尺度、真实光照响应 |
| 地形、草丛、碎石分布 | 程序化地形/分布 + 真实模型 | 覆盖、疏密、接触与通路 |
| 确实没有合适素材的关键物 | 有界自制或生成后人工适配 | 多视角、拓扑/UV/材质、许可、可编辑性 |

素材记录在现有 manifest 上增量补充：

- 实际免费版文件与许可范围；商用许可与再分发许可分别核实。
- 实测尺度、pivot、可用子模型、贴图/alpha 状态。
- 适合的风格和观看距离、明显不适用的场合。
- 接受/拒绝原因，以及 Godot 小样图片。
- 来源/核实时间/文件哈希；远端许可或下载范围变化时重新核实。

**“CC0 + 下载成功 + 导入通过”只是可用性，不是美术适用性。**这正对应四游戏试验里最反复出现的失败。[E3]

### 3.7 让反馈成为有适用范围的记忆，而不是不断增长的禁令

rea-video 把用户纠正保存下来，同源重跑可重用；反复错误会进入复核提示，还可导出为评测标签。它明确不因纠正就悄悄修改分类权重。[R6]

EnvArt 可以区分：

- 项目通用约束：主要可见内容素材优先；真实渲染和可编辑场景交付。
- 当前任务决定：这个空间是室内；这次保持指定白盒。
- 已验证的资产经验：某个模型 alpha 需要单独处理；某种缩放会损害形体。
- 案例教训：这张参考要求连续大体块，不能选有显著板块重复的素材。

每条保留出处、适用范围与反例。不能把“本次墙面不该有这种缝”变成“所有混凝土都不许有缝”，也不能把一次选材失败归结为所有免费素材都差。[E2][E3]

记忆应绑定具体资产/参考/任务版本。换了参考、白盒、资产或材质之后，旧结论要标记需重核，而不是静默沿用。

### 3.8 分离昂贵的取证与便宜的重评，但不滥用旧截图

rea-video 可用已存特征重新分类、生成计划和报告，不必每次重解码；测量实现变化则通过指纹使相关缓存失效。[R4][R8]

EnvArt 对应的原则：

- 仅修正文字、问题优先级或候选排序：可以复用原轮次截图。
- 修改几何、资源、材质、灯光、相机或渲染设置：旧截图不能证明新结果，必须出新图。
- 修改共享材质：复核所有受影响机位，而不只看当前视图。
- 截图与场景版本、依赖、相机和渲染条件一起记录；新轮次不覆盖旧证据。

已有 freeze 文件是良好起点，但个别文件哈希不自动等于完整依赖可复现。[E4] 初期只补本次修改直接影响的资源，不建设复杂缓存调度系统。

## 4. 不应该照搬的部分

### 4.1 不把 rea-video 的数字当成普适可靠性

它的评测文档本身说明：部分 holdout 已因调参失去独立性；同制作来源可能跨集合；缓存特征与重新解码的结果不同；第一次遇到的带货样本只用工具为 46.4%；同时加入 VLM 和 Agent 并非总是更好。[R8]

借鉴的是记录分歧、暴露局限和保留新样本的办法，不是“多 Agent 投票就可靠”，更不是为环境美术制造一个总分来替代看图。

### 4.2 不照搬整个框架和模块数量

`aspects` 把一个问题的测量、提问、解释、报告和评测放在一起，这种组织方式值得学。[R9] 未来表面、道具、光照等维度可以各自拥有相关规则，避免一个变化同时修改多处。

但当前先用几组清楚的问题和证据记录即可，不急着建插件注册器、通用调度器、数据库或模型商城。也不需要新增控制器、交互面板、全量玩法回归。

### 4.3 不把“规划能力”说成“自动执行能力”

rea-video 文档说明，报告中的多镜生成计划与自动生成执行还有差别；部分流程依赖外部工具或手工补交素材，尚未替换的镜头可保留原片占位。[R10]

EnvArt 更应分别标记：候选已发现、许可已核实、已下载、实机已检查、已装配、已看图、用户已接受。灰盒和缺件可以保留，但必须明确未完成，不能混进成品截图冒充完成。

### 4.4 不忽略三维与版权差异

视频最终可以逐帧成立；可试玩环境必须在附近机位和实际空间里成立。不能用生成图片、单面卡片或后期修图代替要求可近看的主体建筑。

参考图用于学习视觉关系，不等于获得其中游戏资产的使用权。素材来源、授权和可交付范围仍必须独立核查。

### 4.5 不让生成器覆盖人工编辑

rea-video 的部分 Markdown 是明确可重建产物；Godot 场景却同时是用户的可编辑成果。不能直接迁移“删除生成目录再写”的方式。[R2][E1]

短期继续用另存场景/独立新增节点/明确的覆盖提示。真的需要增量重建时，再补内容归属、锁定范围、变更预览与冲突中止；没有明确归属时不得自动覆盖人工内容。

## 5. 建议的最小工作流程

```text
白盒 + 精确参考 + 保护要求
          ↓
参考拆解：事实 / 推断 / 目标 / 不确定点
          ↓
主体候选小样：建筑 + 整墙/地表 + 少量代表性 props
          ↓
看实际渲染：不匹配就回到选材，不扩场
          ↓
一个完整活动区域：空间、道具组、表面、光照
          ↓
重新加载保存场景 → 固定机位 + 邻近视角出图
          ↓
问题清单 → 有范围修订 → 新轮次对照
          ↓
用户判断 + 可编辑交付 + 有范围的经验记录
```

关键不是“阶段更多”，而是**把高代价错误提前发现**：错的建筑选型，应在摆几个代表性构件时失败，而不是铺完全场之后靠调色和加箱子补救。

如果逐渐提取工具，优先三个真正能减少重复劳动的深模块：

1. **素材检查**：输入候选文件，输出尺度/依赖/材质风险与预览；许可证据另行保留，工具不凭模型文件判定授权。
2. **出图与冻结**：输入保存场景和既有机位，输出带版本关系的截图；隐藏重载、等待渲染和命名细节，拒绝覆盖冻结轮次。
3. **复核发布**：输入截图与评价，生成紧凑索引和 HTML；不改场景，不自动宣称美术通过。

只封装实际重复出现的工作。现阶段不抽象多引擎 adapter，也不把所有构建脚本改成一个声明式场景语言。

## 6. 分阶段落地与停止条件

### 阶段 A：整理一个现有案例，不重做美术

- 用当前室内局部做资料组织样本，关联现有参考、三个机位、manifest、前后图与未解决问题。
- 新增轻量入口和复核字段，不移动大型素材，不改默认场景。
- 明确这是组织方式验证，不是重启已停止的 Poly Haven 写实方向；正式复刻/流程基线仍按项目约定采用 `7119a84`、`b81f512`。[E1]

**验收**：另一位 Agent 只读入口和一个区域记录，就能指出哪些能改、主要差距是什么、应该打开哪张图，以及结果是否经过用户接受。

### 阶段 B：下一次制作只加“候选小样检查点”

- 用户指定一个方向和局部范围。
- 少量主体候选，先在目标比例、材质和光照下出图。
- 候选不合适就淘汰或适配；用户允许的范围内才进入装饰。

**验收**：参考中最重要的形体/表面偏差能在铺场景之前被发现。记录首次结果和反馈后结果，不能混成一次成功。

### 阶段 C：出现重复劳动后，再抽工具

- 统一冻结出图和报告生成；复用现有机位和脚本。
- 增加必要的关联/状态检查，例如缺图、旧截图、无许可证据。
- 每个独立阶段只做相关检查并单独提交，不连带改已有用户文件。

**验收**：减少重复记录与误覆盖；不能以工具数或代码量增加作为收益。

### 暂缓

- 全网自动素材搜索与全自动采购。
- 一次生成完整关卡或同时推进多个风格。
- 自动总分决定美术是否合格。
- 新增 Agent 编排平台、控制器、复杂编辑 UI、多引擎兼容层。

建议衡量的结果是：主体选型被否决得是否更早、相同问题是否反复出现、局部修改是否影响其他机位、用户达到可接受结果需要多少轮。少量案例先作过程记录，不包装成统计基准。

## 7. 是否需要直接接入 rea-video

**现在不应作为核心依赖。**当前主要输入是静态参考和白盒，环境任务最难的部分也不是区分实拍与 AI。[E1]

以后如果输入变成游戏漫游视频，可以选用 rea-video 辅助抽取关键帧、镜头信息和参考索引。但输出仍要转成空间理解与素材决策；不能假设它已经能恢复房间几何、材质参数、Godot 灯光或可编辑场景。我们自己已有的固定机位巡检，则应优先使用已知相机与场景数据，不必从渲染视频重新猜测。

**一句话方向：把 EnvArt 从“根据参考拼场景”，推进为“有证据的环境拆解与重建流程”；先提高美术决策质量，再自动化重复执行。**

## 8. 2026-11-18 代码复核：下一步只补三个工作环节

本轮只做阅读、代码核对与建议收敛。rea-video 仍为 `ebe853e`；EnvArt 阅读基点已到 `abf6d67`，新增了 [ENVIRONMENT.md](../experiments/whitebox-lighting-study/ENVIRONMENT.md) 和 [review.json](../experiments/whitebox-lighting-study/review.json)。未运行 rea-video、未调用新模型、未改 skill 或 Godot 场景。直接重看了 `control-3.jpg` 与 `detail-01/props.png`，用于核对参考解释和当前问题措辞，不构成新一轮美术验收。

### 实际代码支持什么

| 已核对的实现 | 对我们有用的设计 | 迁移边界 |
| --- | --- | --- |
| `review.build_tasks()` 给出图片、问题与优先级；不展示另一个 VLM 的答案 | 先看图形成观察，再对照历史评价，减少照抄；每个问题指向具体证据 | 环境的优先级应看画面影响和返工成本，不照搬分类置信度阈值 |
| `cli.cmd_apply_review()` 调用 `apply_answers()` 后立即 `finalize()`；后者重新生成逐镜计划、制作单元及报告 | 看图结果必须改变下一步制作决定，报告、入口与问题状态一起更新 | 这条链路重新推导计划，不等于已经执行复刻；我们的“已修改”也不能直接变成“已通过” |
| `report.write_reports()` 调用 `videomd.write()`，两类报告来自同一份数据 | 继续沿用已有入口、manifest、review 和截图，不再增加一套大 JSON 场景副本 | `videomd.write()` 会删除再生成其目录；不能把这种行为用于用户手工编辑的 `.tscn` |
| `aspects/base.py` 并列测量、VLM、Agent 来源；`memory.reapply()` 按源文件标识和时段重用用户纠正 | 区分用户约束、可测事实、视觉观察和实现假设；经验要有适用范围 | 不是自动学习出美术标准，也不是多模型一致就能压过用户意见 |
| `production.py` 将镜头重组为制作单元，`pipeline.decode_fingerprint()` 区分测量与重评代码 | 按区域/共享材质修改，按受影响机位复核；只改文字时可复用图 | 它不是三维资源依赖系统；改材质或灯光后不能用旧截图证明新结果 |

以上均为静态代码检查，未验证该项目运行效果。特别是 `finalize()` 的复核闭环值得学，分类投票、颜色直方图和模型能力路由并不提供可直接移植的环境素材审美筛选算法。

### ① 素材筛选：从“单件能用”推进到“一组值得继续做”

现有 skill 已要求检查代表素材，但还缺少明确的进入装配条件。建议在 **Choose a coherent asset family** 之后补一个短检查点：

- 从参考中挑 3–5 条最影响观感的特征，写清对应图片与区域，例如连续墙体、建筑比例、家具年代、磨损程度、细节尺度；另列本轮必须避免的偏差。
- 围绕最大风险比较少量候选，通常 2–3 个足够，不为每个纸张小件都做竞赛。比较主体建筑/整墙或地表，并带上几件会相邻出现的代表性 props。
- 在目标尺寸和观看距离下用 Godot 渲染。先排查材质/几何本身，再看目标灯光下是否匹配；必要时临时使用清楚的检查光，不能靠暗光隐藏选材缺陷。
- 在已有 manifest 中补“小样图、接受/拒绝原因、可接受的适配”。主体比例或表面语言不成立时返回检索；不要先铺全场再靠调色和小件补救。

这不是新增用户审批关卡：Agent 可在已授权目标内筛选与淘汰，遇到必须改变目标风格或保护范围的取舍时才需要用户决定。

### ② 风格统一：把判断标准与实现方案分开

统一不只是调到同一个色调。每组候选至少比较建筑/物件比例、轮廓复杂度、纹理细节尺度、粗糙度响应、磨损程度及题材年代，并区分“彼此协调”与“贴合参考”。纸箱多、贴图大或都叫混凝土，都不是成立证据。

当前问题队列提供了很好的起点，但不能直接作为无需复核的施工单：

- `W-01` 建议增加施工分格，这是 Agent 的实现假设。参考图确有大尺度构造边界，但用户明确要求消除明显 tile 痕迹；下一轮应保留连续表面候选，只比较有具体图像依据、尺度克制的构造处理，不能把“加缝”列为必达项。
- 重看当前 `props.png`，墙上已有可见颗粒和色差。下一步应判断这些信息是否足以体现混凝土，而不是把上一轮一概记作“没有纹理”，导致重复返工。
- `ENVIRONMENT.md` 的 R1 范围写 x=7.29–9.56，但其包含的交接车节点位于 x=5.85。区域说明不能替代真实节点和白盒约束；下次使用时应核对节点归属，修正或删除不准确的坐标摘要。无需为此开发空间索引框架。

建议在 skill 的参考拆解和复核段落明确：**用户决定是约束；视觉观察需指图；实现建议是待比较的方案。** 经验写在具体案例中，只把跨案例确实反复成立的原则加入通用 skill。

### ③ 实机反馈：每轮只关闭少数关键问题

沿用已有 `review.json`，不用再建设评审平台。一次挑 1–3 个视觉影响最大的事项，记录要改的区域/材质、预期变化及影响机位；实际保存并重开场景后出图，再更新状态：

```text
发现问题 → 选定局部修订 → 已修改待出图 → 已看图复核
                                      ↘ 未改善则保留问题，换方案或回退
用户接受单独记录，不能由上述状态自动推出
```

只在确实有修改时补 `changes`，只在看过新图后补 `verified_in` 和结论；不要求空字段齐备。改变共享墙面材质时重看所有受影响机位，只修文档时不重渲染。若一轮只是加复杂度而没有改善画面，应保留旧版并说明失败，不无限叠加 props。

### 模型尝试与实施顺序

2026-11-18 当前会话的协作工具实际列出了 `gpt-6.2-sol` 和 `gpt-6.2-astra`。这是可用性证据，不是视觉质量或 computer use 提升的实测；本轮没有启动它们，也没有切换主会话模型。

后续可先用 6.2 做一个有边界的试跑：给相同参考、白盒保护、候选文件和固定视角，让它先独立列出最重要的三个差距，再做一组主体选材小样。初次观察不提供旧 Agent 的自评分，用户约束始终提供；随后再对照历史问题。若要比较模型，用相同输入、工具与时间范围，记录实际模型、素材版本和首次结果，不把模型变化与 skill 改动混在一起归因。computer use 只在资产网站或编辑器操作确有需要时评价，不为测试操作能力增加 UI 步骤。

建议顺序：**精简补入上述三个 skill 检查点 → 在一个既有局部做候选小样 → 根据实际画面决定是否继续装配。** 先不抽 CLI、注册器、数据库、通用调度器或多模型投票系统；目前不需要把 rea-video 安装为核心依赖。阶段 A 已有文档入口，下一项产出应该是更可靠的选材决策和实机小样，而不是更多框架文件。
